# Design: add-customer-portal（客户 Web 门户 + 管理后台）

- Change: `add-customer-portal`
- 阶段：MVP6 之后的第一批后续 change 之一；和 `add-credential-proxy` 并列，都是 MVP6 开工前 / 开工后要补的缺口。本 change 不依赖 MVP6 的部署代码，但租户隔离和 VM 状态页要和 MVP6 的隔离规则对上。
- 时间：2–3 周（估计值，本地 agent 按第 0 步盘点后确认）

## 1. 架构图（文字版）

```
  客户（飞书群）─────────────┐
      │ 说话 / 看日报 / 点审批卡 │ MVP1-MVP3 已有
      ▼                      │
  ┌──────────────────────────────────────────────────────┐
  │  控制面                                                 │
  │    身份：飞书 open_id → tenant_id（客户登录也用这套）     │
  │    Ticket / 审批记录 / 预算 / 审计日志（MVP2a/2b 已有）    │
  │    巡检 / 记忆 / 技能（MVP4/MVP5 已有，只读展示）          │
  │    审批状态机：待处理 → 已批准 / 已拒绝（一次变迁）        │
  │    租户隔离：每个接口服务端强制 tenant_id，不靠前端藏      │
  └──────────────────────────────────────────────────────┘
        │                                    │
        ▼                                    ▼
  ┌───────────────────────┐        ┌───────────────────────┐
  │ 客户 Web 门户           │        │ 管理后台                 │
  │ OpenMausBot 前端改     │        │ 另一套页面，不给客户看      │
  │ 只能看自己租户          │        │ 能跨租户看               │
  │ 能改：巡检时间/预算/    │        │ 能看：所有客户 VM 状态、   │
  │   Bot 开关/定时任务     │        │   消耗账单、审批审计、     │
  │ 不能改：核心技能/凭证/  │        │   销户导出               │
  │   别人数据/控制面规则   │        │ 能改：核心技能哈希（走审批）│
  └───────────────────────┘        └───────────────────────┘
        │                                    │
        └────── 手机 / iPad / 电脑都能开 ──────┘
              会话在控制面，不在某台设备上
```

**读图规则**：三层前端，同一套控制面数据。飞书是主入口，客户 Web 是自助和审计，管理后台是运营。权限一层比一层大，隔离在服务端，不在前端。

## 2. 借鉴谁

- **Hermes Hearth（v0.23.0）**：一个网关管所有会话，桌面工作区通过浏览器 tab 提供，手机、iPad、电脑打开是同一份会话。本 change 的客户 Web 就按这个思路：会话在控制面，不在本地 App。
- **OpenMausBot 现有前端**：Bot 列表、聊天、Bot 设置、模型选择、Trigger、审批卡片，这些现成的页面当底子改，不要从零写一个。改的是“谁能看、能看谁的、能改什么”，不是聊天界面本身。
- **Muse**：审批是系统级卡片，真相在控制面一条记录里；双通道只是两个显示器。
- **Grok Bot**：客户在 VM 上注册邮箱、Bot 代操作那套，凭据的事走 `add-credential-proxy`，本 change 不碰。

## 3. 关键决定

### 3.1 客户登录：第一版只做飞书扫码，不设密码

- 客户打开客户 Web，扫飞书码登录。控制面拿扫码得到的 `open_id`，映射到 `tenant_id`（MVP1 白名单就是同一套认人逻辑）。
- 同一租户多人：老板 + 运营各扫各的码，登录后是同一个租户，但角色不同。管理员能改设置，普通成员只能看、只能批被指定给他的审批。
- 不设密码登录：不存密码、不做找回密码、不做密码强度。管理后台登录单独做，见 3.6。
- 登录态：控制面发短期会话，过期重新扫码。会话里只写 `tenant_id` + 角色，不写别的东西。

### 3.2 客户 Web 门户：复用 OpenMausBot 前端，改成客户版

页面清单（第一版只做这 6 页，多了就是扩范围）：

| 页 | 能看什么 | 能改什么 |
|---|---|---|
| Bot 列表 | 他的采购 / 跟单 / 巡检 Bot，各自在干什么、开还是关 | Bot 开 / 关 |
| Ticket 与审批 | 他的 Ticket、审批记录，谁批的、在哪边点的、什么时候、为什么 | 点“允许 / 拒绝”（双通道，见 3.5） |
| 消耗 | token 花了多少、业务花了多少钱，两本账分开 | 预算上限（管理员才能改） |
| 定时任务 | 巡检几点跑、日报几点发、哪些任务开着 | 巡检频率、日报考点、任务开 / 关 |
| 记忆与技能 | 长期记忆、技能列表 | 不能改核心技能；一般记忆只能提修改建议，不能直接写 |
| 设置 | 审批人名单 | 审批人名单、预算上限 |

- 聊天主界面本身不重新设计：左边 Bot 列表、中间聊天、右边设置还是原来的样子。改的是数据范围（只看自己租户）和权限（有些按钮没有）。
- 手机、iPad、电脑都能开：Web 页面响应式，会话和审批状态在控制面，换设备看到的是同一份。

### 3.3 客户能改 / 不能改的边界（服务端强制）

- 能改的，服务端也要验：改巡检时间、预算上限、Bot 开关、定时任务开关、审批人名单，接口里必须带登录身份的 `tenant_id`，改的只能是这个租户的东西。
- 不能改的，前端藏起来不够，服务端要拦：
  - 核心技能（采购 / 付款 / 删数据）：改接口直接 403，MVP5 的哈希校验还在。
  - 真凭证：看不到、改不了，只能授权和吊销（走 `add-credential-proxy`）。
  - 别的客户的数据：跨租户查直接 403。
  - 控制面规则：四层审批、工具白名单、预算熔断，客户改不了。
- 每次改设置都要记审计：谁改的、什么时候、改了什么、改前改后是什么。审计存在控制面，客户 Web 上能看到他自己的改动记录。

### 3.4 管理后台：另一套页面，不给客户看

- 登录：单独的管理员账号，不走客户飞书扫码那套。管理员账号本身能吊销，操作核心技能、销户、导出数据要二次确认。
- 能看的：所有客户列表、每个客户的 VM 状态（醒 / 睡、资源用量）、每个客户的消耗和账单、每个客户的审批和审计日志。出问题能追到是哪条 Ticket、哪个 Bot、谁批的。
- 能做的：租户开通（按 MVP6 流程开 VM）、租户关停（先导出再彻底删除，有删除记录）、改核心技能哈希（要走审批，不能直接改）。
- 不能做的：管理后台也不能直接看到客户的真凭证，只能看到连接状态（正常 / 已降级 / 已吊销）。

### 3.5 双通道审批：飞书和网页都弹，真相只有一条记录

- 有新的审批要人点，控制面同时推给两边：飞书群里弹一张卡，网页待办里多一条。两边显示的是同一条审批记录的同一个状态。
- 用户在任何一边点了“允许 / 拒绝”，控制面做一次原子状态变迁（复用 MVP2b `server/approvals/store.ts` 的原子条件更新）：待处理 → 已批准 / 已拒绝，只能变一次。
- 另一边收到状态推送后立刻变“已处理”，显示“已由 XX 在飞书 / 网页批准”，再点没用。两边同时点，只有一个生效，审计里只记一笔，记清在哪边点的、谁点的、什么时候。
- 两边都要验身份：飞书验点击人的 `open_id` 是不是审批人；网页验登录的人是不是同一个审批人。身份对不上，点不了。
- 过期、吊销、重复点，和 MVP2b 一样：过期卡无效，重复点不算数。

### 3.6 租户隔离：服务端强制，不靠前端藏

- 每个客户 Web 的接口，服务端都按登录身份强制带 `tenant_id` 查。前端只传“我想看我的”，服务端决定“你是谁、你能看谁的”。
- 管理后台跨租户查是另一套权限：管理员角色才能跨租户，客户角色跨租户直接 403。
- 列表、搜索、导出、审计，都要带 `tenant_id` 过滤。导出一个客户的数据，只能导出这个客户的，不能导出全部。
- 测隔离要测“直接调接口”：登录客户 A 的账号，直接调接口拿客户 B 的 Ticket，必须 403，不是只在页面上看不到。

## 5. 风险

- 租户隔离只做了前端隐藏。防法：服务端强制 `tenant_id`，直接调接口测跨租户 403。
- 双通道审批两边结果不一样。防法：真相只有一条记录，原子变迁一次，另一边推送失效。
- 客户 Web 登录绕过飞书身份。防法：第一版只做飞书扫码，不设密码；角色在服务端分。
- 管理后台权限过大。防法：管理员账号单独体系，核心技能、销户、导出要二次确认 + 审计，管理员账号能吊销。
- 客户在 Web 上改了设置，Bot 那边没生效。防法：设置写控制面，Bot 下次执行前从控制面读；改完要在页面上显示“已生效 / 下次执行生效”，不要让客户以为改了就立刻生效。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
