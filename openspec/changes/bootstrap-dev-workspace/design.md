# 开发工作区设计

## 项目背景

基线为 `5987204e33d1115334038b60484e4670ed89b736`，当前本地分支为 `main`。根目录已有 `AGENTS.md`，`apps/docs/CLAUDE.md` 已通过 `@AGENTS.md` 引用同目录指令。仓库已有 `docs/verification/README.md`、`docs/plans/`、`docs/specs/` 和 PR 模板。本地采用稀疏检出，缺少的已跟踪文档可用 `git show HEAD:<路径>` 阅读。拟实施时按目标目录补齐实际源码和测试。

## 本次目标与范围

首版目标是让两种客户端的人类确认和交接语义一致。允许开发者先调查、在当前变更目录写提案，并在换客户端后保留同一份判断依据。先按仓库工作约定实行。强制只读运行环境、受保护的 PR 审批、提交到远端、飞书产品开发和 microVM 部署均留给单独变更。

## 设计决定

1. **每种信息只有一个维护位置。** 项目目标和跨变更决定在 `openspec/WORKSPACE.md`；已接受的行为在 `openspec/specs/`；本次意图、方案和验收在变更目录；任务完成情况在 `tasks.md`；实际源码以 Git 和当前差异为准；交接写最近一个可继续工作的检查点。已有上游文档用路径引用。
2. **先展示、再授权。** 调研、讨论、提案和交接允许先做。产品源码、测试、配置、依赖及正式规范的实施，在维护者通过可追溯的原始消息或评审确认当前提案后开始。展示改动、影响、验收、恢复办法和版本。无歧义的“按这版做”有效；无须固定口令。确认条目必须能追溯到维护者，模型生成的同意文字没有授权效力。
3. **分别记录确认与进度。** 确认是“待确认／已确认／被替代／已撤回”；实施是“未开始／进行中／阻塞／待验收／已验证”。OpenSpec 显示材料齐全，或任务打勾，都不能单独充当人的确认、程序测试或验收记录。关键目标、范围、验收条件及对外影响改变时升版；已确认范围内拆步骤、补证据只更新进度。
4. **按动作取资料。** 回答进度用交接首段；目标不明时才查活动索引。首次实施时接回本版提案、授权原始出处、当前任务、目录约定、适用规范及目标差异。依赖设计取舍时读相应设计章节。查完整历史与验证证据放在审计、追溯或解决矛盾时。跨设备需要双方都能取得的提交、分支或补丁；新会话无法核对原对话时，使用维护者转交的确认或可访问的评审凭据。
5. **减少并发覆盖。** 一个活动变更同时有一名主执行者。分开开发的任务各用独立分支或 worktree；交接记录标出负责人、涉及路径和基线。遇到重叠路径先协调；过期记录向当前执行者核实。两个 worktree 的本地文档不构成实时锁。
6. **证据跟着变更走。** 交接写明已运行的命令、结果、对应代码版本或工作树差异，以及尚未验证项。服务端或会话行为按仓库验证规范启动隔离 fixture；UI 按 `DESIGN.md`。验收通过再同步正式规范、归档；中止的尝试单独标注其结果。

## 风险与取舍

- 首版依赖遵循仓库规则的客户端。能运行任意命令的本地工具仍可以自行写盘。若要技术上禁止提前修改，另提“规划时只读挂载源码、仅开放提案写入区；批准后切换可写 worktree”的变更；PR 审批可另外控制合并。
- 控制文件数量。每次接手只维护短交接；常规设计取舍留在当前 `design.md`，仅跨变更且仍有效的决定进入项目总览。飞书接入、每用户 microVM 等意向只列为候选事项，不因写入总览获得实施授权。
- 稀疏检出与远端同步会影响文件可见性。实施者动手前核对实际基线、目标分支和本地差异；共享记录与现场冲突时，先记录差异再恢复工作。

## 采用步骤

先保留上游目录结构，新增开发工作区入口；下游新工作逐步采用该流程，不批量搬迁历史提案。采用显式的 `openspec/config.yaml` 和已有 CLI 即可使用标准材料。若日后启用客户端专有快捷指令，先展示它将生成哪些工具文件，再单独决定是否接入。
