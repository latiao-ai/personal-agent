# 开发工作区验收规范

## Purpose

开发智能体可以从仓库中查到维护者的决定、实际开发进度和验证证据。换一个没有聊天历史的会话，也能接手正确的变更。

## ADDED Requirements

### Requirement: 从仓库恢复开发状态

工作区必须（SHALL）提供统一入口，供开发智能体查阅二开项目的优先事项、正在进行的变更、适用的仓库规则和可核实的交接证据。

#### Scenario: 新智能体在没有聊天记录时接手

- **WHEN** 新智能体打开同一项目版本，并取得对应工作树或移交的补丁
- **THEN** 它能从仓库中找到当前变更、负责人、提案版本、授权状态、最近一次已验证的结果和下一步
- **AND** 它会在继续开发前核对实际分支与本地差异

#### Scenario: 只问当前进度

- **WHEN** 用户给出活动变更名，交接首段完整且问题只涉及最近记录
- **THEN** 智能体从根规则和交接首段报告版本、负责人、授权、最近验证与下一步，按需指出证据位置

#### Scenario: 摘要缺失或与现场冲突

- **WHEN** 旧交接缺少摘要，或摘要与任务、基线、当前文件矛盾
- **THEN** 智能体按问题补读任务、提案、历史或相应差异，说明尚未核实的状态，待事实一致后继续实施

### Requirement: 维护者确认后再实施

实施前必须（SHALL）取得维护者对当前提案版本及其范围的明确确认，并保留可核实的出处。

#### Scenario: 提案材料齐全，维护者尚未确认

- **WHEN** OpenSpec 显示规划材料齐全，但维护者尚未确认当前提案
- **THEN** 智能体仅开展调研或修订规划材料，实施文件和正式规范保持原状

#### Scenario: 实施范围超出已确认版本

- **WHEN** 已确认的飞书私聊功能需要扩展到群聊
- **THEN** 智能体写明新增范围、提高提案版本，并在维护者确认新版本后才实施扩展部分

#### Scenario: 首次写入与连续实施

- **WHEN** 智能体准备首次实施，或换人、换工作树、上下文压缩后恢复实施
- **THEN** 它核对本版提案、真实授权出处、当前任务、适用规范和目标差异；依据缺失、撤回或不符时暂停写入
- **AND** 已确认范围内接着编辑或补测可沿用确认；现场变化时复核受影响的路径

### Requirement: 并行开发与交接

每项活动变更都必须（SHALL）记录一名当前主执行者、所用分支或工作树，以及涉及的文件路径。

#### Scenario: 两项变更涉及同一文件

- **WHEN** 另一位智能体准备编辑已有执行者正在修改的文件
- **THEN** 双方先约定由谁修改，或拆开各自的改动，再动手编辑，并将决定写入相应变更的交接记录

### Requirement: 归档保留验收证据

归档完成的变更时，必须（SHALL）随变更保留验证证据和尚未解决的事项。

#### Scenario: 任务已勾选，约定的验证尚未执行

- **WHEN** 实施任务全部勾选，但约定的验证尚未执行
- **THEN** 交接记录标明“待验证”，变更保留在活动目录

#### Scenario: 下一位智能体查阅已归档的变更

- **WHEN** 已通过验证的变更完成归档
- **THEN** 智能体能从正式规范中查到已接受的行为，并从归档的交接记录中找到验证结果及其出处
