# Design: MVP1.5 架构决策 `decide-tenancy-architecture`

- Change: `decide-tenancy-architecture`
- 类型：只写文档，不改代码
- 时间：2–3 天

## 1. 边界图（文字版）

```
                        ┌─────────────────────────────────┐
                        │  控制面（厂商云端，常驻）          │
                        │                                 │
  飞书用户 ──► IM 网关 ──► 租户与身份 ──► Ticket / Mandate 存储 │
                        │    │              │ 审批记录        │
                        │    │              │ 预算计数        │
                        │    │              │ Vault           │
                        │    │              │ LLM 转发代理     │
                        │    │              │ 审计日志        │
                        │    │              │ 长期记忆 / 技能库 │
                        │    ▼              ▼               │
                        │  签名 Mandate（只读副本）          │
                        │  内部虚拟 Key（带租户标识）         │
                        │  核心技能（只读挂载 + 哈希校验）     │
                        └──────────────┬──────────────────┘
                                       │ 仅走少数已开放接口
                                       │ VM 之间互不可达
                        ┌──────────────▼──────────────────┐
                        │  用户 VM（一用户一台 microVM）      │
                        │                                 │
                        │  OpenMausBot 运行时                │
                        │  （openmausbot serve）            │
                        │  会话 / 工作记忆 / 技能只读副本     │
                        │  浏览器 / 工作文件                 │
                        │  带签名的 Mandate 只读副本          │
                        └─────────────────────────────────┘
```

**读图规则**：控制面是策略与持久权威数据的唯一写入方。VM 可发起受限请求取得执行所需的只读副本或 token；返回值仍由控制面签发和裁定。VM 之间网络互不可达，VM 只能访问控制面显式开放的少数接口和出口代理，不能直连控制面内部接口。VM 里可写的数据丢失后可恢复或重建；真正用于约束 agent 的策略和凭据不放在 agent 可写位置。图中的租户边界对应 2.1、宿主机与网络对应 2.2、数据边界对应 2.3、引擎代理对应 2.4、许可证对应 2.5、上游隔离同步对应 2.6。

## 2. 六个决策

### 2.1 租户粒度：已确认，一用户一台 microVM

- 一台云服务器上运行多个用户，**每个用户一台 microVM，同一用户的多个 Bot 共享这台 VM**。
- 用户的个人数据、浏览器登录、记忆、技能都在 VM 里。
- 用户之间靠 VM 硬隔离；同一 VM 内的 Bot 之间只做权限区分（各自的工具白名单和工作目录），不做硬隔离。
- 以后支持“企业客户下有多个用户”时，企业这一层只在控制面里做（成员、策略、共享技能模板、汇总计费），不改变“一用户一 VM”的模型。
- 影响：MVP2 的 Ticket 按用户记账，MVP5 的记忆与技能按用户分，MVP6 的隔离按用户做。不要再写“一客户一台 VM”这种含糊说法，统一写“一用户一台 VM”。

### 2.2 宿主机规范

宿主机是所有用户共享的故障域和攻击面，定 4 条：

| 项 | 规范 |
|---|---|
| 资源配额 | 每台 VM 设 CPU、内存、磁盘、带宽配额，防止某个用户拖慢其他人。建议默认值（**待 MVP6 验证后定终值**）：2 vCPU、4 GB 内存、20 GB 持久磁盘、带宽按需限速。空闲 VM 休眠，释放内存；记录单机密度和唤醒延迟 |
| 网络隔离 | VM 之间网络默认互不可达。VM 只能访问控制面开放的少数接口和经过出口代理的外网，不能直接访问其他 VM、不能访问控制面内部接口 |
| 明文数据 | 宿主机持久层不存用户明文数据或凭据；用户 VM 持久卷静态加密，解密密钥由控制面管理。VM 运行时会在来宾内存中处理用户数据，宿主机属于受信任基础设施边界 |
| 容量与迁移 | 定好单机容纳几台 VM、允许超售多少，满了怎么迁移到下一台服务器。迁移方式：持久磁盘可迁移，或用快照恢复。MVP6 之前要有一份“单机密度 + 唤醒延迟”的实测记录 |

单机密度和 CPU / 内存超售比例目前没有环境数据支持，标记为 **MVP6 前待实测确认**，不伪造固定台数。MVP6 以同时运行的活跃 VM 数、冷启动/唤醒 p50 与 p95、宿主机资源余量、磁盘吞吐为记录项；达到预留余量阈值后停止在该宿主机分配新 VM，并迁移持久磁盘或从一致性快照恢复到新宿主机。VM 间网络策略需在宿主机虚拟网络/防火墙层执行，出口代理按租户身份限流并拒绝内网、云元数据和控制面管理网段。

### 2.3 控制面与 VM 的边界

| 放在哪 | 放什么 | 谁能写 | 谁能读 | 丢了怎么办 |
|---|---|---|---|---|
| VM 外（控制面） | IM 网关、租户与身份 | 控制面服务 | 控制面服务 | 控制面有备份，VM 不受影响 |
| VM 外（控制面） | Ticket 与 Mandate 存储 | 控制面（Engine 是唯一写工单的人） | VM 只能读带签名的只读副本 | 控制面有备份；VM 里的副本只是副本 |
| VM 外（控制面） | 审批记录、审计日志 | 控制面 | 控制面；用户在 dashboard 查 | 控制面有备份；VM 里最多留一份副本，不能只存在 VM 里 |
| VM 外（控制面） | 预算计数 | 控制面 | 控制面 | 预算嵌在替身 token 里，见 2.4 |
| VM 外（控制面） | Vault | 控制面 | 控制面；agent 永远看不到真实凭据 | 控制面有备份 |
| VM 外（控制面） | LLM 转发代理 | 控制面 | 控制面 | 见 2.4 |
| VM 外（控制面） | 长期记忆、技能库、核心技能只读源 | 控制面（每晚复盘写记忆；技能入库在控制面） | VM 启动时只读一份下来 | 控制面有备份；VM 丢了能恢复 |
| VM 内 | OpenMausBot 运行时（`openmausbot serve`）、会话、工作记忆、技能只读副本、浏览器和工作文件、带签名的 Mandate 只读副本 | VM 内的 agent（会话、工作记忆、工作文件） | 本 VM 内的 Bot | 工作记忆丢了不可惜；长期记忆在控制面有备份 |

**三条细化规则（2026-11-26 补充，解决“记忆和技能全在 VM 里 agent 能自己改”的问题）：**

1. **记忆分两层**：VM 内只放工作记忆（当前会话、正在做的事）；长期记忆（客户偏好、规则、白名单）在控制面，每晚复盘写进去，VM 每次启动只读一份下来。
2. **技能只锁核心**：核心技能（采购、付款、删数据）锁死，存一份哈希在控制面，运行时校验，不一致就拒绝加载，agent 自己改不了，只能人到控制面改。**其他技能不分档、不审批**，agent 自己提、自己改、自己用，改完留记录，改坏了回滚到上一版。
3. **Mandate 带签名**：控制面发 Ticket 时带签名 / 哈希，VM 里存带签名的只读副本，执行前先验签，改一个字签名就失效。修改 Mandate 等于新建一张 Ticket，用 `parent_id` 关联旧单，旧单状态改为 `superseded`。

### 2.4 引擎接入：第三方中转站 API Key，经控制面代理

- **已确认**：接入第三方中转站的 API Key（OpenAI / Anthropic 兼容端点，见 `docs/custom-engines.md`），不用本机订阅登录的 `claude` / `codex` CLI。
- **关键安全要求**：中转站总 Key 放在控制面 LLM 代理层（如 LiteLLM 或自建转发），**不要直接明文放进用户 VM**。
- VM 只拿带租户标识的内部虚拟 Key 访问代理，由控制面统一做限流、按用户 / Bot 计费、预算熔断和中转站切换。
- 内部虚拟 Key 应为短期、可撤销、限定租户和用途的凭据；不得包含或可反推出中转站总 Key。代理逐请求校验租户、Bot、模型白名单和额度，并维护幂等用量账本；到预算上限即拒绝后续请求。中转站故障时仅在兼容且策略允许的供应商间切换，保留原租户额度与审计记录。
- 预算要嵌在替身 token 里：控制面每次给 VM 发 token 时，签名声明包含 token 有效期、租户 / Bot、模型或工具范围以及本次花费上限。代理按签名声明和控制面剩余额度双重校验，超额拒绝；token 不授予 VM 对控制面数据的写权限，也不能单靠 VM 自行校验实现最终扣费。
- 当前 `docs/custom-engines.md` 描述的是 OMB 直接读取用户配置中的 provider key（配置文件权限为 0600，但 `environment` 值仍是明文）；它没有实现租户虚拟 Key、控制面代理、按用户 / Bot 用量核算或预算熔断。因此该文档仅证明 OpenAI-compatible 端点可接入，MVP6 仍需新增代理与凭据注入路径，不能把现有自定义引擎描述为已满足托管架构。
- Hermes 等外部 agent 后续仍可评估作为 ACP 引擎接入，但不 fork。
- 影响：MVP2 的预算计数要区分“模型 token 花费”和“业务花费（下单金额）”，两者分别设上限。现有 `spend.ts` 只管前者。

### 2.5 `enterprise/` 目录：先保留，用前必须二选一

- **已确认：先保留继续用。**
- 需注意 `enterprise/LICENSE` 条款：开发、测试与评估免费（无 `OMB_LICENSE_KEY` 时默认跑 OSS 版）；但生产启用、对外托管（host for third parties / SaaS）或白标必须向版权方（Milind Soni）取得商业/合作授权，且不得绕过 license 校验或未经授权分发。
- 上线对外售卖前**二选一**：买正式托管授权，或把用到的一小块能力迁到自研控制面后删除该目录。
- 私有部署与许可证：Apache 2.0 允许闭源分发衍生版本，但必须保留 `LICENSE`、`NOTICE` 和第三方许可证，`third_party/cua-driver/` 等组件也有各自条款。`enterprise/` 目录不能未经授权分发。

#### 当前实际能力清单

| 能力 | 当前实现 | 生产 / 托管影响 |

### 2.6 上游同步：每 2 周一次，单独 change

- 建立 `upstream` 远程，记录每次同步的上游提交号，**每 2 周同步一次**，单独开 change（例如 `sync-upstream-YYYYMMDD`），在隔离环境里跑全量测试。
- **新功能尽量不改核心文件**：网关、Ticket、策略中心、控制面放在新目录或独立服务里，只通过 HTTP API、驱动接口（`server/contracts.ts`）或少量钩子接入 harness。核心文件的修改集中记录在一份清单里，同步时重点检查这些文件。
- **删模块优先“不打包”，其次“关闭”，最后才“删除”**：删得越多，上游同步时冲突越多。桌面端、语音、本机控制这类模块，可以在 VM 镜像构建时不打包，源码先保留。
- OpenMausBot 迭代很快，当前版本 0.1.178，而本仓库历史只有 3 个提交，同步时不要直接合，要先在隔离环境测。

## 3. 待核对项（在实现阶段继续验证）

| 核对项 | 当前结果 | 后续动作 |
|---|---|---|
| 2 vCPU / 4 GB / 20 GB 是否够跑 `openmausbot serve` | 建议默认值已记录，缺少目标 microVM 镜像和宿主机上的测量数据 | MVP6 前测常驻内存、冷启动/唤醒时间与单机密度，再定终值 |
| `server/local-vm-*.ts` 能否改成 microVM 调度器 | 已盘点：现有代码管理本机容器 VM、Bot 会话租约与 seat affinity，不是云端 microVM 编排器 | MVP6 复用生命周期状态管理概念；单独建设 provider、宿主机调度、持久盘迁移/快照能力 |
| MVP1 网关是否松耦合 | 已核对：独立 Python 进程，只通过 localhost HTTP API 与 harness 通信；当前仍与 harness 同机部署 | MVP6 将其作为控制面服务部署并增加租户到 VM 的路由 |
| `docs/custom-engines.md` 是否满足代理方案 | 不满足托管隔离要求：当前 provider key 由 OMB 从配置环境读取，尚无租户虚拟 Key 和控制面代理 | MVP6 新增代理和凭据注入，不将现有直连配置当作已完成方案 |
| `enterprise/` 实际能力与许可 | 已盘点 `whitelabel`、`admin`、`budgets`、`billing`；`sso` 仅 planned，详见 2.5 清单 | MVP6 前取得书面托管授权，或迁出所需能力并删除该目录 |

## 4. 对后面 MVP 的影响（防返工清单）

| MVP | 按本文怎么做 |
|---|---|
| MVP2a `add-ticket` | Ticket 存在控制面，不存在 VM 里。开发阶段可先放在 harness 的独立 SQLite 文件里，但要通过接口访问，以后好搬。只给会产生副作用的工作生成 Ticket，普通对话不生成。observe 只用在外部事件来源 |
| MVP2b `add-approval` | 审批记录、Vault、预算计数都在控制面。飞书审批卡片要校验点击人的 `open_id` 必须是批准人，同一张卡片重复点击要幂等。凭据代理可拆成单独 change `add-credential-proxy` |
| MVP3 `add-routing` | 飞书网关在控制面，先按飞书 `open_id` 找到用户和对应 VM，再在 VM 内按会话或频道路由到具体 Bot。网关作为唯一消费者，一个 App ID 只能有一个长连接 |
| MVP4 `add-readonly-patrol` | 巡检 Ticket 的 Mandate 工具白名单里只能有读接口，权限代理按白名单拦截。巡检结果分档在控制面记 |
| MVP5 `add-memory-skill` | 长期记忆与技能库在控制面，VM 内只放工作记忆与技能只读副本。核心技能锁死（哈希在控制面），其他技能不分档、不审批。同一 VM 内多个 Bot：哪些记忆是用户级共享，哪些是 Bot 私有，要在 design 里写清 |
| MVP6 `add-isolation-deploy` | 按 2.1–2.3 实现：每个用户一台长期 microVM，带持久磁盘；用户之间硬隔离；同一用户多 Bot 共享 VM，只做权限区分。审计、审批、Ticket 在控制面，VM 里最多留副本 |
