# Design: add-approval（审批，MVP2b）

- Change: `add-approval`
- 阶段：MVP2b，MVP2a 之后、MVP3 之前
- 时间：1 周左右（MVP2 共 1–2 周，2a / 2b 各约一半；复用盘点后以 tasks.md 为准）

## 1. 架构图（文字版）

```
Ticket（MVP2a 已生成）
  │ 字段：id、Mandate、工具白名单、预算、状态
  ▼
┌──────────────────────────────────────────────┐
│  审批分层（控制面，硬规则在前，模型在后）        │
│                                              │
│  第 1 步：代码规则（白名单、预算、动作类型）      │
│    ├─ 不在白名单 → 第 4 层：交回给人 / 直接拒    │
│    ├─ 超预算 → 第 4 层：交回给人 / 直接拒        │
│    └─ 动作类型是只读 → 第 1 层：直接做           │
│                                              │
│  第 2 步：评审模型（只看一般写操作）             │
│    ├─ 只能把风险往上调，不能往下调              │
│    ├─ 超时 / 报错 / 输出无法解析 → 第 3 层       │
│    └─ 不能决定是否放行花钱类动作                │
│                                              │
│  第 3 步：人（飞书审批卡片）                    │
│    ├─ Allow once / Always allow / Deny        │
│    ├─ 校验 open_id 必须是批准人                │
│    ├─ 同一张卡片重复点击要幂等                  │
│    └─ 卡片过期后点击无效                       │
│                                              │
│  第 4 步：交回给人                             │
│    └─ 超预算 / 不在白名单 / 评审判有风险        │
└──────────────────────────────────────────────┘
  │ 批了 → 执行（VM 内，拿临时替身 token）
  │ 不批 / 拒了 → 不执行，有日志
  ▼
审计记录（控制面）：谁批的、批了什么、什么时候批的、花了多少钱
```

**读图规则**：顺序是固定的，不能跳。代码规则先拦，评审模型再看，人最后点。评审模型不是决定人，它只是个“往上调风险”的助手。

## 2. 借鉴谁

- **OpenAI dots**：四层审批（直接做 / 智能审批 / 先问人 / 交回给人）+ Auto-review，密码、转账强制人接管。
- **Hermes**：三层审批（smart / manual / off），smart approval 不能替代人对大额采购的审批。
- **Muse**：Sentinel 底子，真实凭据在 vault，agent 只拿临时替身 token，审批是系统级卡片，不是聊天消息。
- **OpenMausBot 现有模块**：`docs/approval-levels.md`、`server/permission-proxy.ts`、`auto-approve.ts`、`always-allow.ts`、`decision-log.ts`、`spend.ts`、`harness-budget.ts`、`cloud-secrets.ts`。

## 3. 关键决定

### 3.1 四层审批

| 层 | 名字 | 适用 | 怎么做 |
|---|---|---|---|
| 1 | 直接做 | 只读：查库存、查订单、查价格、查物流 | 不弹卡片，直接回 |
| 2 | 智能审批 | 一般写操作：写备注、改非关键字段、发内部通知（不对外） | 先让评审模型看，模型只能往上调，不能往下调；模型判有风险 → 第 3 层 |
| 3 | 先问人 | 花钱 / 下单 / 付款 / 删数据 / 对外发消息 | 必须弹卡片，点了才执行，不点不执行 |
| 4 | 交回给人 | 超预算 / 不在白名单 / 评审判有风险 / 评审模型超时或报错 | 不执行，交回给人，有日志 |

**注意**：第 2 层不是“模型批了就能做花钱的事”。花钱类动作永远在第 3 层，评审模型不能放行。

### 3.2 硬规则在前，模型评审在后

顺序固定：

1. **代码规则**：白名单、预算、动作类型。写死在代码里，不要让模型判断。
   - 不在白名单 → 第 4 层
   - 超预算 → 第 4 层
   - 动作类型是只读 → 第 1 层
   - 动作类型是花钱 / 下单 / 付款 / 删数据 / 对外发消息 → 第 3 层，不经过第 2 层
2. **评审模型**：只看一般写操作。
   - 只能把风险往上调，不能往下调。代码规则判第 2 层，模型最多调到第 3 层，不能调到第 1 层。
   - 超时、报错或输出无法解析时，一律按“先问人”处理（失败即拒绝），不要直接执行。
   - 评审模型读到的工具参数里可能夹带提示注入，所以不能让它决定是否放行花钱类动作。
3. **人**：飞书审批卡片，见 3.3。

### 3.3 审批卡片（飞书）

- 卡片上写清楚：做什么、花多少钱、给谁、有什么风险、对应哪张 Ticket（id）。
- 按钮：Allow once（只批这一次）/ Always allow（以后同类都批）/ Deny（拒绝）。
  - `Always allow` 要谨慎：只对同一发起人、同一动作类型、同一预算范围内的同类 Ticket 生效，不要写成“以后所有事都批”。
- **单独接入回调权限**：MVP1 没开卡片回调。本 change 要补上飞书交互卡片的回调权限（`card.action.trigger`）。
- **校验点击人**：点击人的 `open_id` 必须是这张 Ticket 的批准人（Mandate 里的 `approver`）。非批准人点击，无效并有日志。
- **幂等**：同一张卡片点两次，只执行一次。第一次点击后 Ticket 状态已变，第二次点击查到状态已不是“待审批”，直接返回“已处理”，不重复执行。
- **过期**：卡片过期后点击无效。过期时间写在 Mandate 的 `valid_until` 里，过期后 Ticket 状态改为 `cancelled` 或 `superseded`，不要执行。

### 3.4 凭据 vault 与临时替身 token

- 真实凭据放 vault，Agent 只拿临时替身 token，用完失效；每个客户 vault 分开。
- Composio 的 OAuth 连接已经由代理持有凭据，可以直接复用。
- 自建业务系统的凭据，建议通过控制面的出口代理在请求时注入，agent 进程里始终没有真实凭据。**这一项工作量大，拆成单独的 change `add-credential-proxy`，本 change 不做完整注入逻辑**，只做到：
  - Vault 分开（按用户 / 按客户）
  - 临时替身 token 的接口（发 token、过期失效、按 Ticket 绑定）
  - agent 进程里没有真实凭据（写进 specs 的验收里，测的时候查进程环境变量和日志）

### 3.5 预算上限

区分两项，分别设上限：

| 口径 | 说明 | 现状 |
|---|---|---|
| 模型 token 花费 | 调模型花了多少钱 | 现有 `spend.ts` 只管这一项，复用它 |
| 业务花费（下单金额） | 下单、付款花了多少钱 | 现有 `spend.ts` 不管这一项，本 change 新建预算计数 |

上限分三档：单笔 / 日 / 月。超了直接停，不问模型，不弹卡片，直接拒绝并有日志。不要让模型判断“超一点点要不要放行”。

预算嵌在替身 token 里（MVP1.5 已定）：控制面每次给 VM 发 token 时，token 里写着“这次最多花多少钱、能调哪些工具”，超了直接调不通。

### 3.6 审计记录

落库，不能只留在聊天里。记录：

- 谁批的（`open_id`）
- 批了什么（Ticket id、Mandate 摘要、动作、金额）
- 什么时候批的
- 花了多少钱（模型 token + 业务花费，分开记）
- 拒绝的也要记：谁拒的、为什么拒（超预算 / 不在白名单 / 评审判有风险）

审计记录存在控制面（MVP1.5 已定），VM 里最多留一份副本。

## 5. 风险

- 评审模型被提示注入，判花钱为低风险。防法：硬规则在前，评审模型只能往上调，花钱类动作必须弹卡片。
- 评审模型超时，Bot 直接执行。防法：超时一律按“先问人”处理。
- 群里其他人代点卡片。防法：校验 `open_id` 必须是批准人。
- 同一张卡片点两次，执行两次。防法：幂等。
- 卡片过期后还能点。防法：过期点击无效。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
