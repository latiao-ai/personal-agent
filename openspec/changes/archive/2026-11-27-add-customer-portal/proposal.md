## 为什么改

2026-11-26 晚用户说清楚了三层分法，之前 MVP 里缺了中间那一层：

1. **客户主入口是飞书群**——这个有了，MVP1–MVP3 都是按这个做的，客户在群里说话、看日报、点审批卡。
2. **客户 Web 页面**——没有单独设计。用户说：可以用现在的 OpenMausBot 前端页面当底子，但要偏审计一点，让客户能改他自己的某些 Bot、看到消耗、看到定时任务。现在 OpenMausBot 前端还是单用户桌面 App 的样子，没有按租户分、没有客户登录、没有“只能看自己”的隔离。
3. **管理后台**——也没有单独设计。用户说：管理要有自己的后台页面，可以看到不同用户的后台信息。现在只有控制面的 API（`/api/tickets`、`/api/approvals`、`/api/routing`、`/api/patrol`、`/api/memory-skill`），没有一个给运营用的、能跨租户看的管理页面。

没有这一层，客户想查账、想改巡检时间、想看上个月花了多少钱，只能在飞书群里问 Bot；运营想看所有客户的状态，只能一个一个去查 API。MVP6 做完能卖了，但卖出去之后，客户和管理都没有一个能用的 Web 入口。

## 改什么（范围）

只做三层前端的 Web 部分，不做飞书群本身（MVP1–MVP3 已做），不做 MicroVM 部署（MVP6）：

1. **客户登录 Web 后台**：第一版用飞书扫码登录。身份就是 MVP1 已有的飞书 `open_id`，扫码后控制面把 `open_id` 映射到 `tenant_id`，不新设密码、不存密码。同一租户多人（比如老板 + 运营）可以各扫各的码，权限分两级：管理员能改设置，普通成员只能看和批自己被指定的审批。客户登录这件事，在 `add-credential-proxy` 里是明确“放到 MVP6 之后再做”的，本 change 就是那个“之后”，现在做。
2. **客户 Web 门户（OpenMausBot 前端改）**：复用现在的前端当底子，改成客户版，偏审计和自助。手机、iPad、电脑都能开，会话在控制面（和 Hermes 一个网关管所有会话的思路一样），走到哪都是一份：
   - 他的几个 Bot：采购、跟单、巡检，各自在干什么、开还是关
   - 他的 Ticket 和审批记录：每一条是谁批的、在哪边点的（飞书还是网页）、什么时候、为什么
   - 他的消耗：token 花了多少、业务上花了多少钱，两本账分开（MVP2b 的双口径）
   - 他的定时任务：巡检几点跑、日报几点发、哪些任务开着、哪些关着
   - 他的记忆和技能：长期记忆、技能列表，只能看，不能直接改核心技能
3. **客户能改的东西（只能改他自己的）**：巡检频率、日报考点时间、审批人名单、预算上限、某个 Bot 开还是关、某个定时任务停还是不停。改完要记审计：谁改的、改了什么、改前改后是什么。
4. **客户不能改的东西**：采购、付款、删数据三个核心技能是锁死的（MVP5 已定）；Vault 里的真凭证看不到、改不了，只能授权和吊销（走 `add-credential-proxy`）；别的客户的数据一个都看不到；控制面的规则（四层审批、工具白名单、预算熔断）改不了。
5. **双通道审批**：审批卡飞书和网页都弹。控制面里同一条审批记录，飞书卡片和网页待办都是它的显示。两边任何一边点了“允许/拒绝”，另一边立刻变“已处理”，再点没用；两边同时点，只有一个生效（复用 MVP2b 的原子条件更新）。记录里记“在哪边点的、谁点的”。
6. **管理后台（另一套页面，不给客户看）**：只有运营能进，能跨租户看：
   - 所有客户列表，每个客户对应哪个 VM，VM 是醒着还是睡着，资源用了多少
   - 每个客户的消耗、账单、审批、审计日志，出问题能追到是哪条 Ticket、哪个 Bot、谁批的
   - 租户开通和关停：新客户怎么开 VM，老客户不用了怎么先导出再彻底删除（MVP6 的流程，这里是操作入口）
   - 核心技能哈希、控制面规则，只能管理改，改了记审计

## 不动什么（边界）

- 不改飞书群的交互：客户主入口还是飞书群，群里 @、日报、审批卡的流程不变（MVP1–MVP3 已定）。
- 不改四层审批的规则：直接 / 智能审批 / 问人 / 交回，这四档不变；双通道只是多了一个点的入口，不是多了一档审批。
- 不改 MVP5 的核心技能锁：客户在 Web 上改不了核心技能，管理后台改核心技能也要走审批和哈希校验。
- 不改 MVP6 的隔离：客户 Web 只能查到他自己的 `tenant_id`，管理后台跨租户查是另一套权限；租户隔离是在服务端强制的，不是前端藏起来的。
- 不做 Bot 代填账号密码：凭据的事走 `add-credential-proxy`，本 change 不碰真凭证。
- 不做完整 Ontology 页面：记忆和技能页面只展示 MVP4 的库存/订单最小字段和 MVP5 的偏好/规则，全量 Ontology 是后续 change。

## 验收标准

- [ ] 客户用飞书扫码能登录客户 Web，登录后只能看到他自己的 Bot、Ticket、审批、消耗、定时任务；换一个客户的账号登录，看不到上一个客户的任何数据。
- [ ] 客户在 Web 上改巡检时间、预算上限、Bot 开关，改完立即生效，审计里有“谁、什么时候、改了什么、改前改后”。
- [ ] 客户在 Web 上点不了核心技能的修改入口；直接调接口改核心技能也被服务端拦下，不是只在前端藏起来。
- [ ] 一条审批同时在飞书和网页上出现；在一边点了，另一边立刻变“已处理”；两边同时点，只有一个生效，审计里只记一笔，记清在哪边点的。
- [ ] 管理后台能看到所有客户的 VM 状态、消耗、审批和审计；客户账号登录管理后台被拒绝；管理账号改核心技能哈希要走审批。
- [ ] 手机、iPad、电脑打开客户 Web，看到的是同一份会话和同一条审批状态，不是一台设备一份。
- [ ] `openspec validate --all --strict --no-interactive` 通过；`tasks.md` 全勾完；`handoff.md` 写清楚。

## 风险

- 租户隔离只做了前端隐藏。防法：每个接口服务端都按登录身份强制带 `tenant_id` 查，跨租户直接 403；前端藏起来不算隔离，要测“直接调接口拿别人数据”。
- 双通道审批两边结果不一样。防法：真相只有控制面那一条记录，原子条件更新只允许一次状态变迁，另一边收到状态推送后失效。
- 客户 Web 登录绕过飞书身份。防法：第一版只做飞书扫码，不设密码登录；管理员和普通成员的权限在服务端分，不在前端分。
- 管理后台权限过大。防法：管理登录单独的账号体系，操作核心技能、销户、导出数据都要二次确认 + 审计；管理账号本身也要能吊销。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
