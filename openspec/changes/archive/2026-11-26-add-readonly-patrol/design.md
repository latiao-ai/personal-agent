# Design: add-readonly-patrol（只读巡检，MVP4）

- Change: `add-readonly-patrol`
- 阶段：MVP4，MVP3 之后、MVP5 之前
- 时间：3–5 天

## 1. 架构图（文字版）

```
定时 Trigger（每天一次，手动也能触发一次）
  │ 复用现有 routine：routine-run-gate.ts
  │ 上一次没跑完就跳过，有运行时限
  ▼
┌──────────────────────────────────────────────┐
│  巡检 Ticket（只读 Ticket）                    │
│  复用 MVP2a TicketEngine                       │
│                                              │
│  Mandate 工具白名单：只有读接口                │
│    ✓ 读库存、读订单、读价格、读物流             │
│    ✗ 写数据、发消息、付款、控浏览器             │
│  权限代理按白名单拦截，模型想调写接口也会被拒    │
│  提示词说“不要写”不算数，工具层说了算            │
└──────────────────────────────────────────────┘
  │ 读数据源（先过适配器，输出规范字段）
  ▼
┌──────────────────────────────────────────────┐
│  数据源适配器（第一版只做通 2 类）              │
│                                              │
│  库存：sku / available_quantity（件）           │
│       / warehouse / checked_at                 │
│  新订单：order_id / status / paid_at            │
│       / amount / sku_list                      │
│                                              │
│  价格、物流、供应商回复、爆品信号：              │
│  第一版只留接口定义和空实现，不接真实数据源      │
│  映射表在控制面，不在 VM 里                     │
└──────────────────────────────────────────────┘
  │ 小模型巡检（只查增量，用缓存和摘要）
  ▼
┌──────────────────────────────────────────────┐
│  结果分档（三档）                              │
│                                              │
│  没问题 → 只写记录，不打扰人                    │
│  小问题 → 写日报（一天一次）                    │
│  大问题 → 生成执行 Ticket，带证据，              │
│          走 MVP2b 审批                         │
└──────────────────────────────────────────────┘
```

**读图规则**：巡检本身永远只读，唯一能“动”的是生成执行 Ticket，而执行 Ticket 还要走审批。巡检不直接发消息、不直接下单、不直接改数据。

## 2. 借鉴谁

- **OpenMausBot routine**：定时 Trigger 已有，`routine-run-gate.ts` 已经处理了“上一次没跑完就跳过”和运行时限。
- **OpenAI dots**：只读巡检，读接口白名单，小模型巡检，发现异常再用大模型。
- **Hermes**：技能沉淀里的 Curator 思路，巡检发现的重复问题以后可以沉淀成技能（那是 MVP5 的事，本 change 不做）。

## 3. 关键决定

### 3.1 巡检是定时 Trigger，不是群聊消息

- 巡检由定时 Trigger 触发，每天一次，手动也能触发一次。不要让巡检走 MVP3 的群聊路由，群聊是人说话才触发，巡检是时间到了就触发。
- 复用现有 routine：`server/app-triggers.ts`、`server/bot-automations.ts`、`server/routine-*.ts`、`routine-run-gate.ts`、`routine-event-receipts.ts`、`routine-recovery.ts`。先盘点，再动手，不要重写定时器。
- 上一次没跑完，下一次跳过，不重叠跑。单次巡检有运行时限，超时就停，记一条超时记录。

### 3.2 只读在工具层强制执行，不能靠提示词

这是本 change 最重要的一条，写三遍都不多：

- 巡检 Ticket 的 Mandate 工具白名单里只能有读接口，没有写、没有发消息、没有付款、没有控浏览器。
- 权限代理（`server/permission-proxy.ts`）按白名单拦截：模型就算想调用写接口，也会被拒，有拒绝记录。
- 提示词里写“你不要写、不要发消息”只是辅助，**不算数**。真正说了算的是工具层。
- 测试必须包含一条：巡检时提示词诱导模型发消息，被工具层拦截，有拒绝记录。没有这条测试，等于没测只读。

### 3.3 第一版只做通 2 类，其余 4 类只留接口

| 类别 | 第一版 | 怎么做 |
|---|---|---|
| 库存 | 做通 | 假数据：SKU 库存低于安全库存，能发现并升级 |
| 新订单 | 做通 | 假数据：新订单进来，写进日报；已付款超 24 小时未发货，升级 |
| 价格 | 只留接口 | 接口定义 + 空实现，不接真实数据源 |
| 物流 | 只留接口 | 接口定义 + 空实现，不接真实数据源 |
| 供应商回复 | 只留接口 | 接口定义 + 空实现，不接真实数据源 |
| 爆品信号 | 只留接口 | 接口定义 + 空实现，不接真实数据源 |

6 类一起上，3–5 天做不完。先把库存和新订单这两类做通，验证“只读 → 分档 → 升级”这条链路，后续 change 再一类一类接真实数据源。

### 3.4 最小规范字段（Ontology 的最小起步）

巡检不直接读平台原始字段。每个数据源先经过适配器，输出统一的规范字段：

- **库存**：`sku`、`available_quantity`（单位：件）、`warehouse`、`checked_at`
- **新订单**：`order_id`、`status`（只用 Ontology 标准状态，例如 `paid_unshipped` / `shipped` / `delivered`）、`paid_at`、`amount`、`sku_list`

映射表放在控制面，不在 VM 里。例如淘宝 `stock`、Shopify `inventory_quantity`、京东 `stockNum`、ERP `on_hand_qty`，都映射到 `available_quantity`。状态码也要建对照表，不要靠模型猜。

**不做全量 Ontology**：不定义 10 个实体、300 个关系，不上图数据库。本 change 只做这两类的最小规范字段和映射表，全量 Ontology 放在 MVP5 / 后续 change 里。

### 3.5 省 token

- 小模型巡检：日常巡检用小模型，发现异常再用大模型看一遍。
- 只查增量：只查上次巡检之后新增 / 变化的数据，不全量扫。
- 用缓存和摘要：同一批数据只读一次，摘要存下来，下次直接读摘要。
- 日报一天一次：小问题攒到日报里一起发，不是一条问题发一条消息。
- 订单按事件触发：新订单进来就触发一次增量巡检，不用等每天一次。

巡检的 token 花费要记在预算里，和 MVP2b 的双口径预算分开记：巡检 token  spend 单独记一笔，不要和工作 token 混在一起。

### 3.6 结果分档（三档）

| 档 | 条件（示例） | 怎么做 |
|---|---|---|
| 没问题 | 库存都高于安全库存，没有新订单异常 | 只写记录，不写日报、不生成 Ticket、不打扰人 |
| 小问题 | 库存接近安全库存（例如只剩 1.5 倍安全库存）、新订单正常但量比平时多 | 写日报，一天一次，攒到一起发 |
| 大问题 | 库存低于安全库存、已付款超 24 小时未发货、价格异常波动 | 生成执行 Ticket，带证据（SKU、当前库存、安全库存、缺口、订单号、时间），走 MVP2b 审批 |

大问题生成执行 Ticket 时，Ticket 里必须带证据，不要只写“库存不足了”。证据至少包括：哪个 SKU、当前库存多少、安全库存多少、缺口多少、什么时候查到的。没有证据的 Ticket，审批人没法批。

### 3.7 控制面 / VM 边界（MVP1.5）

- 巡检 Ticket、Mandate、审批记录、审计日志都在控制面，不在 VM 里。
- 数据源适配器和映射表在控制面，VM 里的巡检只能读控制面给的规范字段，不能直接连平台数据库。
- 巡检结果（记录 / 日报 / 执行 Ticket）也写在控制面，VM 里最多留一份副本。

## 4. 待核对（开始写代码之前，在本地核对这 6 项）

- [ ] `server/routine-*.ts`、`routine-run-gate.ts`、`routine-event-receipts.ts`、`routine-recovery.ts` 的真实入口：定时 Trigger 现在是怎么跑的？“上一次没跑完就跳过”是怎么实现的？
- [ ] `server/app-triggers.ts`、`server/bot-automations.ts`：MVP2a 复用的 Trigger 链，巡检能不能直接挂上去？
- [ ] MVP2a 的 `server/tickets/classifier.ts` 和 `TicketEngine`：巡检发现大问题时，怎么生成执行 Ticket？不要重写分类器和引擎。
- [ ] `server/permission-proxy.ts`、`auto-approve.ts`、`always-allow.ts`：权限代理现在是怎么按白名单拦截的？巡检的只读白名单能不能直接配出来？
- [ ] `server/spend.ts`、`harness-budget.ts`：token 花费现在是怎么记的？巡检 token 能不能单独记一笔？
- [ ] 库存和新订单的假数据：现在有没有现成的 fixture？没有的话，先写 2 套假数据，一套正常、一套库存不足，再写代码。

## 5. 风险

- 模型被提示注入带偏。防法：只读在工具层强制执行，巡检 Ticket 的 Mandate 写死“只读，不执行”。
- 6 类数据源一起上，做不完。防法：第一版只做通库存和新订单，其余 4 类只留接口。
- 全量扫 token 爆掉。防法：小模型巡检、只查增量、缓存和摘要、日报一天一次。
- 巡检误报太多，人就不看了。防法：结果分三档，没问题只写记录，不打扰人。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
