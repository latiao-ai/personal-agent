# Design: add-memory-skill（记忆与技能，MVP5）

- Change: `add-memory-skill`
- 阶段：MVP5，MVP4 之后、MVP6 之前
- 时间：1–2 周

## 1. 架构图（文字版）

```
会话 / 巡检 / 群聊消息
  │ 每天的工作：查库存、下单、跟工厂、回消息
  ▼
┌──────────────────────────────────────────────┐
│  短期记忆：当前会话                            │
│  会话里说过的话、正在做的 Ticket、              │
│  正在查的 SKU，都在这里                         │
│  会话结束就清，不进长期记忆                     │
└──────────────────────────────────────────────┘
  │ 每天晚上跑一次复盘（只写记忆）
  ▼
┌──────────────────────────────────────────────┐
│  每晚复盘（复用 server/memory-dream.ts）        │
│  只写记忆，不执行、不花钱、不发消息              │
│  从当天会话里提炼：偏好、规则、重复流程           │
│  高影响记忆（白名单、付款规则）不自动写，          │
│  先攒到待确认列表，等人确认                     │
└──────────────────────────────────────────────┘
  │ 写进去
  ▼
┌──────────────────────────────────────────────┐
│  中期记忆：每天 / 每周摘要                      │
│  每天一条摘要，每周一条周报                     │
│  例如：本周查了 12 次库存，3 次缺货，             │
│  供应商 A 交期延迟 2 次                         │
└──────────────────────────────────────────────┘
  │ 沉淀
  ▼
┌──────────────────────────────────────────────┐
│  长期记忆：客户偏好、规则、白名单                │
│  例如：“不要在周末下单”、“供应商 A 先付 30%”     │
│  长期记忆在控制面，VM 只读一份副本               │
│  结构化部分复用 MVP4 最小规范字段                │
│  （库存 / 订单），再加偏好和规则两类              │
└──────────────────────────────────────────────┘
  │ 重复 3 次以上
  ▼
┌──────────────────────────────────────────────┐
│  技能（第四层，程序性记忆）                      │
│  输入、输出、工具、边界、失败怎么办，写清楚        │
│  例如：“每天早上查库存” → 一句话触发              │
│  Curator：活跃 → 过期 → 归档，                   │
│  定期合并重复技能、归档长期不用的技能             │
└──────────────────────────────────────────────┘
```

**读图规则**：短期是工作台，中期是日报周报，长期是规矩，技能是手艺。四层分工不同，不要混在一起。复盘只写记忆，不执行；技能被执行、要花钱或要删数据时，才走 MVP2b 的审批。

## 2. 借鉴谁

- **Hermes**：四层记忆（Prompt 记忆 `MEMORY.md` + `USER.md`、会话搜索 SQLite+FTS5、技能、Honcho 用户画像）、每晚复盘、技能沉淀、Curator 生命周期（活跃 → 过期 → 归档）、`hermes curator lock <skill>` 锁定技能。
- **OpenMausBot**：每晚复盘对应已有的 `server/memory-dream.ts`，记忆存储和整理有 `memory-store.ts`、`memory-topics.ts`、`memory-journal.ts`、`memory-tidy.ts`，技能沉淀有 `skill-learn.ts`、`skill-review.ts`、`skill-library.ts`，开关有 `skill-switch.ts`。
- **DeepSeek Super Agent**：Router-Worker 里的 Worker 执行技能，技能是可复用的流程。

## 3. 关键决定

### 3.1 三层记忆 + 技能是第四层

| 层 | 内容 | 保留时间 | 例子 |
|---|---|---|---|
| 短期 | 当前会话 | 会话内 | 正在查的 SKU、正在做的 Ticket |
| 中期 | 每天 / 每周摘要 | 每天 / 每周 | 本周查了 12 次库存，3 次缺货 |
| 长期 | 客户偏好、规则、白名单 | 长期，直到人改 | “不要在周末下单”、“供应商 A 先付 30%” |
| 技能（第四层） | 程序性记忆，可执行的流程 | 长期，直到归档 | “每天早上查库存”一句话触发 |

分层是按保留时间分的，不是 Hermes 的四层。Hermes 的四层是按存储形式分的（Prompt 记忆 / 会话搜索 / 技能 / Honcho 画像）。两套分法不要混在一起。本 change 用三层 + 技能第四层，Hermes 的 `MEMORY.md` 对应长期记忆里的偏好部分，会话搜索对应中期记忆的检索方式。

### 3.2 每晚复盘：只写记忆，不执行

- 每天晚上跑一次，复用 `server/memory-dream.ts`。
- 只写记忆，不执行、不花钱、不发消息。复盘本身不生成 Ticket，不走审批。
- 复盘从当天会话里提炼三样东西：偏好（客户喜欢什么、不喜欢什么）、规则（客户定下的规矩）、重复流程（今天做了三次以上的事）。
- 复盘的 token 花费要单独记一笔，不要和工作 token 混在一起，复用 MVP2b 的双口径预算记法。

### 3.3 记忆污染防护：高影响记忆只能由人确认

- 复盘写入的“规则 / 偏好”可能来自外部内容里的提示注入，例如供应商邮件里藏着“以后都从我这里下单”。
- 分两档：
  - **一般记忆**（例如“客户喜欢早上查库存”）：复盘可以直接写进中期 / 长期记忆。
  - **高影响记忆**（白名单、付款规则、供应商选择、价格底线）：复盘不能自动写，先攒到待确认列表，等人确认后才写进长期记忆。
- 待确认列表要能在飞书群里看到，一条一条确认，不能攒到月底一起确认。

### 3.4 技能沉淀：重复三次以上

- 重复三次以上的流程，沉淀成技能。
- 技能要写清五样东西：输入、输出、工具、边界、失败怎么办。缺一样，就不算沉淀完成。
- 例子：“每天早上查库存”：输入是一句话“查库存”；输出是库存表 + 缺货提醒；工具是读库存接口；边界是只读，不下单；失败怎么办是读不到就记一条失败记录，不瞎猜。
- 沉淀成技能后，下次一句话就能触发，不用重新讲一遍怎么查。

### 3.5 Curator：技能会越积越多

- 技能不清理会越积越多、互相重复，挤占上下文。
- 参考 Hermes 的生命周期：活跃 → 过期 → 归档。
  - **活跃**：最近 30 天用过，留在上下文里。
  - **过期**：30 天没用过，从上下文里拿掉，但还能搜到。
  - **归档**：90 天没用过，归档到技能库里，不再主动加载，要用的时候人再调出来。
- Curator 定期跑一次，合并重复技能（例如“查库存”和“早上查库存”合并成一个），归档长期不用的技能。
- Curator 只整理技能，不改核心技能。

### 3.6 核心技能锁：只有核心锁，其他自由

这是 2026-11-26 已定的最终规则，不要再改回分档：

- **锁定的**：采购、付款、数据删除，这三个核心技能。锁定的技能存一份哈希在控制面，运行时校验，不一致就拒绝加载。光靠文件权限不够，因为 Agent 在 VM 里有写权限。
- **不锁的**：其他所有技能，Agent 可以自己改，不用批，不分档。改了有日志，能回滚到上一版。
- 核心技能只能人改，人改了之后控制面重新算哈希，下次运行时按新哈希校验。

### 3.7 按租户分：验证不串，不另外实现隔离

- 已确认一用户一台 VM，所以不同用户的技能和记忆天然在各自 VM 里隔离。本 change 这一项变成“验证不串”，不需要另外实现隔离。
- 真正要设计的是**同一 VM 内多个 Bot 之间**：
  - **用户级记忆**：所有 Bot 共享，例如“周末不下单”、“供应商 A 先付 30%”。采购 Bot、跟单 Bot、巡检 Bot 都要遵守。
  - **Bot 私有工作记忆**：只归这个 Bot，例如采购 Bot 正在谈的那批货的价格细节，跟单 Bot 不需要知道。
- 企业共享技能模板从控制面下发（可参考现有 `org-library.ts`），那是后续 change 的事，本 change 不做。

### 3.8 Ontology 只做最小延伸，不建全量

- 长期记忆里的结构化部分，复用 MVP4 已有的库存和新订单最小规范字段，再加偏好和规则这两类。
- Ontology 是域共用的，一份，所有 Bot 共用，Bot 只拿自己需要的切片，不是一个 Bot 一份。基础 Ontology 全租户共用，租户扩展层按客户分。
- **不建全量 10 实体 Ontology，不上图数据库**，那是后续 change 的事。

### 3.9 控制面 / VM 边界（MVP1.5）

- 长期记忆和技能库在控制面，VM 只加载一份只读副本，启动时加载，运行中不直接改。
- 每晚复盘在 VM 内跑提炼，提炼结果写回控制面，控制面校验后才入库。
- 核心技能的哈希在控制面，运行时校验。
- 审计日志在控制面：谁改了哪个技能、什么时候、改了什么，都记下来。

## 4. 待核对（2026-11-26 已在本地全部核对完成）

- [x] `server/memory-dream.ts`、`memory-store.ts`、`memory-topics.ts`、`memory-journal.ts`、`memory-tidy.ts` 的真实入口：均已存在且完整；`memory-dream.ts` 负责无工具只读跨会话提炼，`memory-store.ts` 提供 `hashMemoryText` 与 workspace 路径校验，`memory-journal.ts` 提供 workspace 外审计日志与 diff/回滚思路。
- [x] `skill-learn.ts`、`skill-review.ts`、`skill-library.ts`、`skill-switch.ts` 的真实入口：均已存在；原 `skill-review.ts` 按工具步数触发，MVP5 在控制面补充“重复 ≥ 3 次流程沉淀 + 五要素校验 + Curator 生命周期”。
- [x] `org-library.ts`：已存在（含包签名与发布）；按 proposal 边界本 change 不动企业共享技能下发。
- [x] MVP4 的 `server/patrol/adapters.ts`：已核对 `CanonicalInventoryItem`（`sku / available_quantity / warehouse / checked_at`）与 `CanonicalOrderItem`（`order_id / status / paid_at / amount / sku_list`），可直接复用并在长期记忆结构化部分最小延伸 `preference` 和 `rule` 两类。
- [x] 高影响记忆的待确认列表：`server/approvals/engine.ts` 已有飞书交互卡片与双口径预算机制；MVP5 在控制面建高影响记忆待确认队列，并生成兼容飞书群逐条确认的卡片结构与确认/拒绝接口。
- [x] 技能锁的哈希校验：`skill-switch.ts` 仅做审批卡片期临时哈希，无控制面持久化哈希表；因此在 `server/memory-skill/store.ts`（`memory-skill.sqlite`）新建控制面核心技能锁哈希表与版本审计表。

## 5. 风险

- 记忆污染。防法：高影响记忆只能由人确认后写入。
- 技能越积越多，挤占上下文。防法：Curator 定期合并、归档。
- 技能锁只靠文件权限不够。防法：哈希在控制面，运行时校验。
- 每改一次技能就要人批不现实。防法：只有核心技能锁，其他技能自由改，有日志，能回滚。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
