## 为什么改

- 前面四个 MVP 都是“当下能干活”：私聊通了，工单和审批通了，群聊路由通了，巡检也能每天查一次了。但 Bot 还是没有记性：客户昨天说过“不要在周末下单”，今天周末有单，Bot 照样下；每天早上都要查库存，每天都要重新讲一遍怎么查。
- 要补上越用越聪明的能力：三层记忆记住客户偏好和规则，每晚复盘把当天学到的写进记忆，重复三次以上的流程沉淀成技能，下次一句话就能触发。
- 没有记忆和技能，产品只能当聊天工具卖，卖不出“越用越省事”的价值，MVP6 的多租户也没有可沉淀的东西。

## 改什么（范围）

只加记忆与技能，不改 Ticket 生成、不改审批、不改路由、不改巡检：

1. **先复用，再新建**：每晚复盘对应已有的 `server/memory-dream.ts`，记忆存储和整理有 `memory-store.ts`、`memory-topics.ts`、`memory-journal.ts`、`memory-tidy.ts`，技能沉淀有 `skill-learn.ts`、`skill-review.ts`、`skill-library.ts`，开关有 `skill-switch.ts`。本 change 主要是对照 Hermes 的设计调整分层和触发条件，不是新写。
2. **三层记忆 + 技能是第四层**：短期是当前会话；中期是每天 / 每周摘要；长期是客户偏好、规则、白名单。技能（程序性记忆）单独作为第四层，不混进长期记忆里。分层是按保留时间分的，不是 Hermes 的四层（Prompt 记忆 / 会话搜索 / 技能 / Honcho 用户画像），不要把两套分法混在一起。
3. **每晚复盘**：每天晚上跑一次，只写记忆，不执行、不花钱、不发消息。
4. **技能沉淀**：重复三次以上的流程，沉淀成技能，写清输入、输出、工具、边界、失败怎么办。
5. **按租户分**：A 客户的技能不能给 B 客户用，技能库分开。已确认一用户一台 VM，所以不同用户的技能和记忆天然在各自 VM 里隔离，本 change 这一项变成“验证不串”，不需要另外实现隔离。真正要设计的是**同一 VM 内多个 Bot 之间**：哪些记忆是用户级、所有 Bot 共享（例如“周末不下单”），哪些是 Bot 私有的工作记忆。
6. **核心技能锁**：只有采购 / 付款 / 数据删除这三个核心技能锁定，Agent 不能自己改，只能人改。**其他技能 Agent 可以自己改，不用批，不分档**，改了有日志，能回滚到上一版。这是 2026-11-26 已定的最终规则：每改一次技能就要人重新批不现实，分档更麻烦。
7. **记忆污染防护**：每晚复盘写入的“规则 / 偏好”可能来自外部内容里的提示注入（例如供应商邮件）。高影响记忆（白名单、付款规则）只能由人确认后写入，不能由复盘自动写入。
8. **Ontology 只做最小延伸，不建全量**：长期记忆里的结构化部分，复用 MVP4 已有的库存和新订单最小规范字段（`sku / available_quantity`、`order_id / status / paid_at / amount / sku_list`），再加偏好和规则这两类。**不建全量 10 实体 Ontology，不上图数据库**，那是后续 change 的事。Ontology 是域共用的，一份，所有 Bot 共用，Bot 只拿自己需要的切片，不是一个 Bot 一份。

## 不动什么（边界）

- 不改 Ticket 生成逻辑：那是 MVP2a 已完成的事。
- 不改审批逻辑：那是 MVP2b 已完成的事。技能沉淀本身不走审批，只有技能被执行、要花钱或要删数据时，才走审批。
- 不改路由逻辑：那是 MVP3 已完成的事。
- 不改巡检逻辑：那是 MVP4 已完成的事。巡检发现的重复问题以后可以沉淀成技能，但本 change 不自动把巡检结果转成技能。
- 不做跨客户共享技能：A 客户的技能不能给 B 客户用。企业共享技能模板从控制面下发（可参考现有 `org-library.ts`），那是后续 change 的事，本 change 不做。
- 不做自动改核心技能：采购 / 付款 / 数据删除的核心技能，Agent 不能自己改，只能人改。
- 不做全量 Ontology：不定义 10 个实体、300 个关系，不上图数据库。
- 不改 OpenMausBot 核心的 bot 调度、harness 服务；不删模块。

- [ ] 三层记忆都能写、能读：短期（当前会话）、中期（每天 / 每周摘要）、长期（客户偏好、规则、白名单）。
- [ ] 每晚复盘能跑，只写记忆，不执行、不花钱、不发消息。
- [ ] 技能沉淀能跑：重复三次以上的流程，沉淀成技能，写清输入、输出、工具、边界、失败怎么办。
- [ ] 按租户分：A 客户的技能不能给 B 客户用，验证不串。
- [ ] 同一 VM 内多个 Bot 之间：用户级记忆所有 Bot 共享，Bot 私有工作记忆不串。
- [ ] 核心技能锁能跑：采购 / 付款 / 数据删除的技能锁定，Agent 改了就拒绝加载；其他技能 Agent 可以自己改，有日志，能回滚。
- [ ] 高影响记忆（白名单、付款规则）只能由人确认后写入，复盘不能自动写入。

## 风险

- 记忆污染：复盘把供应商邮件里的指令当成客户规则写进长期记忆。防法：高影响记忆只能由人确认后写入。
- 技能越积越多、互相重复，挤占上下文。防法：补上 Curator，定期合并重复技能、归档长期不用的技能。
- 技能锁只靠文件权限不够，因为 Agent 在 VM 里有写权限。防法：锁定的技能存一份哈希在控制面，运行时校验，不一致就拒绝加载。
- 每改一次技能就要人批不现实。防法：只有核心技能锁，其他技能 Agent 可以自己改，有日志，能回滚。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
