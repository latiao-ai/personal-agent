## 为什么改

`add-customer-portal` 落地之后，登录和消息平台留下了四个断点，用户在 2026-11-27 上午一个一个撞上了：

1. **登录入口是散的，没有一个统一入口。** 主界面 `/` 没有登录（本地单用户），客户门户 `/portal` 是飞书扫码登录，管理后台 `/admin` 是用户名密码登录，三个入口三套账。用户说“一个统一登录，登录后按角色跳转，管理员进后台，普通用户进自己的管理页，才是应该这样设计的”。
2. **飞书扫码登录是坏的，而且修它没有意义。** 客户门户的二维码编码的是 `feishu://openmausbot/qr-login?token=qr_...`，没有手机扫码器和飞书能处理这个自定义 scheme，扫出来只是一行文本；服务端有 `POST /api/portal/auth/qr/confirm`，但没有任何飞书 Bot / 网关 handler 会调用它，扫码永远确认不了登录。用户在 2026-11-27 10:41 明确说这个配对修复“倒是不需要”，登录改走账号密码。
3. **飞书只能接一个固定 Bot，网关也不是常驻的。** MVP1 的网关是 `scripts/feishu_gateway.py`，启动时 `--bot` 写死一个 Bot、`--thread` 写死一个会话，实测接的是隔离测试 Bot `FeishuBaselineProbe`（`e7f85baa-78b8-471d-bcab-fd966ec7d8e5`，隔离 harness 端口 19896），回复是写死的 `hello from fake claude`，主界面 5199 的 Bot 列表里根本找不到它；而且网关是手动跑的 Python 脚本，`pnpm` 启动项目时不带它，终端一关、Mac 一睡、进程一死就断。用户说“虽然接入飞书群聊的 Bot 一般都是 manager bot，但是也要提供用户他自己任意的 bot 都可以接入飞书”。Hermes 的做法是每个 Bot 在自己的 profile 里填消息平台凭据，一个网关进程带多个 Bot，本 change 按这个思路改，但要加上多租户的 `tenant_id` 校验，Hermes 本身是单用户，不能照搬。
4. **模型还在走本地 CLI。** 现在本地每个 Bot 回答时，harness 拉起本机装好并登录的 `claude / codex / grok` CLI。路线图 MVP1.5 早已定好：引擎走第三方中转站 API Key（OpenAI / Anthropic 兼容），经控制面 LLM 代理转发，主 Key 不进用户 VM。本 change 把这一点落地：所有 Bot 统一走中转 DeepSeek，不再依赖本机 CLI 登录。

## 改什么（范围）

只做下面 5 件，全部在同一个 change 里：

1. **统一登录入口 `/login`（账号 + 密码）**
   - 只有一个登录入口 `/login`，账号 + 密码登录，不做手机号，不做飞书扫码登录。
   - 登录后按角色跳转：客户账号 → `/portal`；管理员账号 → `/admin`。
   - `/portal` 和 `/admin` 保留为目的地路由，不删除、不只在前端隐藏；加服务端路由守卫：未登录直接访问 `/portal` 或 `/admin` → 跳 `/login`；登录了但角色不对 → 跳回自己的页面或 403。
   - 原来各页自己的登录框收敛到 `/login`：`/portal` 的飞书扫码登录框、`/admin` 的独立登录框不再是入口，统一走 `/login`。
   - 老账号（本地 OpenMausBot 账号，唐浩南，数据在 Mac 的 `~/.openmausbot`）单独给一个用户名密码登录，供测试用，不绑手机号，不自动新建空租户。
2. **账号注册只能在管理后台做，不开放自助注册；建完自动跳到测试账号**
   - 注册不开放给用户自己注册。账号必须由运营 / 管理员在后台管理页面（`/admin`）里注册。
   - 管理员在 `/admin` 里建账号时，指定用户名、初始密码、角色（客户 / 管理员）、所属租户。密码只存哈希（沿用 `server/portal/admin.ts` 的 scrypt 哈希 + 盐那套，不新发明一套），明文密码不进日志、不进 Ticket、不进飞书群。
   - 建完账号后，管理后台自动跳转到这个新建的测试账号上，方便马上验证。测试账号用户名为 `tanghaonan`（密码由用户在创建时设定，本包不写密码值，也不把密码值写进任何文件、记忆或提交）。
   - 管理员可以停用 / 吊销账号，停用后该账号的会话立即失效，不能再登录。
3. **任意 Bot 接消息平台：飞书 + 个人微信（Hermes 式网关，本次就做常驻）**
   - 飞书不只接 manager bot：用户自己的任意一个 Bot 都能在 portal 里绑定到飞书。企业微信（WeCom）本次不做，延后。
   - 消息平台第一版只做两个：飞书、个人微信（Weixin）。个人微信走 Hermes 的 Weixin 路线：iLink Bot API 扫码登录，生成一个 iLink 机器人身份，私聊为主，一般不能被拉进普通微信群；这与企业微信（WeCom，管理后台建智能机器人，拿 Bot ID / Secret）是两个不同的平台，不要混用。
   - 网关改成 Hermes 式（见 design §4）：
     - 网关是常驻服务（Linux 上 systemd，Mac 上 launchd），跟着项目一起启动，进程死了自动拉起来，WebSocket 断了 SDK 自己重连，不再是手动跑的 `python scripts/feishu_gateway.py`。草稿版曾说“不把网关改成常驻服务”，2026-11-27 14:10 用户确认写入设计后，已改为本次就做。
     - 一个网关进程在控制面，里面按平台分适配器（`FeishuAdapter` / `WeixinAdapter`），收到的消息先统一成内部格式，再按绑定表路由，不再是启动时写死 `--bot` / `--thread`。
     - 每个 Bot 在 portal 里有自己的「消息平台」页：飞书填 App ID / Secret，个人微信走 iLink 扫码，保存后网关热加载，不用重启整个项目。
   - 身份链（见 design §3）：账号 → `user_id` → `tenant_id` → Bot 列表（`Bot.tenant_id`）；绑定表记录哪个 Bot 接了哪个群 / 私聊；登录身份与飞书 `open_id` 之间有一张链接表。
4. **所有 Bot 统一走第三方中转 DeepSeek**
   - 每个 Bot 回答时，模型调用走：Bot → harness → 控制面 LLM 代理 → 第三方中转站 → DeepSeek（OpenAI 兼容端点）。
   - 中转站总 Key 放在控制面 Vault / LLM 代理层，不直接放进用户 VM；VM 只拿带租户标识的临时令牌，由控制面做限流、按用户 / Bot 计费、预算熔断和中转站切换。
   - 本地 `claude / codex / grok` CLI 登录不再是模型路径：新装一台机器，不装 CLI 也能跑；已装 CLI 的机器也不再依赖它。Jev 快分流也可以走中转站的小模型，不用再装本地模型。
   - 模型名以中转站实际支持的为准，示例为 `deepseek-chat` / `deepseek-v4-flash`，以本地核对的中转站文档为准，不要硬编码一个中转站没有的模型名。
5. **测试账号自动跳转**
   - 见第 2 件：管理员建完账号，自动跳到该测试账号上验证。这是本次明确要做的。

## 不动什么（边界）

- 不把执行层换成 Hermes Agent：2026-11-27 14:33 用户决定先不换，继续用 OpenMausBot harness。Hermes 引擎替换的 8 件（模型 CLI→中转、Bot→Hermes profile、记忆、routine、审批、工具、网关、前端）本次不做，记在 handoff 的“延后”里，以后再议。注意：本 change 里做的只是“借 Hermes 网关的分层”，不是“换 Hermes 当执行引擎”，两者不要混在一起。
- 不做手机号注册 / 登录：手机号先不设置，只保留账号密码。以后要做手机号，再开新 change。
- 不修飞书扫码登录的配对：`feishu://openmausbot/qr-login` 那个二维码和 `POST /api/portal/auth/qr/confirm` 没有 handler 的问题，本次不修；统一登录改走账号密码后，扫码登录不再是入口。已有的二维码接口不要删，先留着，但不要再把它当登录入口宣传。
- 不绑老账号和新账号：老账号（唐浩南）单独给一个用户名密码测试用，不做手机号绑定，不自动新建空租户，不做一次性绑定码。
- 不做企业微信（WeCom）：WeCom 适配器本次不写，`WeComAdapter` 只留一个空接口 / 占位，不接 `wss://openws.work.weixin.qq.com`。
- 不改四层审批的规则：直接 / 智能审批 / 问人 / 交回四档不变；统一登录和网关改动不增加一档审批。
- 不改 MVP5 的核心技能锁：采购 / 付款 / 删数据三个核心技能还是锁死的，哈希在控制面校验。
- 不改飞书群的交互本身：群里 @、日报、审批卡的流程不变（MVP1–MVP3 已定）；改的是“哪个 Bot 能接进来”和“网关怎么常驻”，不是群聊流程。
- 不做 Bot 代填账号密码：凭据的事走 `add-credential-proxy`，本 change 不碰真凭证，只做登录账号的密码哈希存储。

## 风险

- 统一登录改错，客户进不了门。防法：`/login` 上线前，先在隔离环境里测“客户 / 管理员 / 未登录 / 错角色”四种情况；上线后保留一次回滚点，能立刻回到旧的各页登录框。
- 账号密码存错地方。防法：密码只存 scrypt 哈希 + 盐，不存明文，不记日志，不进 Ticket；管理员建账号时，初始密码只在创建那一刻显示一次，之后查不到。
- 网关改成常驻服务后，同一个 App ID 有两个长连接消费者。防法：启动时声明“本应用唯一消费者”，`lark-cli` 等同凭据客户端必须停掉；投递按 `event_id` 去重，飞书重投不重复回复。
- 绑定表写错，消息发给错的 Bot / 错的租户。防法：网关收到消息先验 `tenant_id`，再验 `bot_id`，两个都对不上就拒绝并记日志；绑定表改动记审计。
- 中转站 Key 泄露。防法：总 Key 只在控制面 Vault / LLM 代理层，VM 只拿临时令牌，令牌过期、吊销、超预算都立即失效；不要把 Key 写进代码、日志、镜像。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
