# Design: add-isolation-deploy（隔离与部署，MVP6）

- Change: `add-isolation-deploy`
- 阶段：MVP6，MVP5 之后，最后一个 MVP
- 时间：4–8 周（新版 roadmap 的时间，不是旧版的 2–4 周）

**读图规则**：控制面是大脑 + 账本 + 图书馆，虚拟机是手 + 眼睛。VM 里能写的东西，都是丢了也不可惜、改了也伤不到别人的；真正用来约束的，都在控制面，VM 只能读，不能改。知识库的本体也在控制面，VM 只是去借书，不是藏书。

## 2. 借鉴谁

- **Grok Bot / Muse**：每用户一台 Firecracker microVM，硬件级隔离；同一用户的多个 Bot 共享一台 VM，不做 Bot 间硬隔离。
- **Hermes**：单网关拥有所有会话，控制面思路。
- **OpenMausBot**：现有 `server/local-vm-*.ts`（租约、座位池、配置），看能不能改造成 microVM 调度器，不要从零写调度器。

## 3. 关键决定

### 3.1 先做技术验证，再写正式代码

从 MVP2 就应该开始抽时间做，每周抽半天，一项一项验证，不要等到 MVP6 才开始选型：

1. **选型**：Firecracker / Cloud Hypervisor / Kata，或云厂商的轻量 VM。先比冷启动时间、常驻内存、持久磁盘支持、快照支持，再定。
2. **`openmausbot serve` 无界面运行在 VM 里的冷启动时间和常驻内存**：到底要几秒启动、常驻吃多少内存，实测，不要猜。
3. **持久磁盘加快照的备份与恢复**：VM 坏了，能不能用快照恢复；恢复要多久；备份存在哪里。
4. **现有 `server/local-vm-*.ts` 能否改造成 microVM 调度器**：租约、座位池、配置这三样，能不能直接复用，不能的话要改哪里。

验证结果要写进 handoff.md，选型定了才能开工。选型不定，代码写了也可能要推倒重来。

### 3.2 一用户一台 microVM，带持久磁盘

- 一用户一台 microVM，带持久磁盘；同一台服务器上运行多台。
- VM 长期存在，不是随用随弃。状态、会话、工作文件存在持久磁盘上，VM 重启还在。
- 建议默认值 2 vCPU / 4 GB / 20 GB，待 MVP6 验证后定稿。不要一上来就给 8GB，成本扛不住；也不要只给 1GB，`openmausbot serve` 跑不起来。
- 审计记录不要只存在 VM 里：VM 里的东西 Agent 都能改。审计、审批、Ticket 应该存在控制面，VM 里最多留一份副本。

### 3.3 用户之间隔离：文件、网络、登录，三样都要隔

- **文件**：A 用户看不到 B 用户的文件、订单、浏览器登录。
- **网络**：A 用户 VM 内的 Agent 主动扫描网络，访问不到 B 的 VM 和控制面内部接口。VM 之间网络互不可达，VM 只能访问控制面接口和出口代理。
- **登录**：浏览器登录、账号、Cookie，各自在各自 VM 里，不串。

只做文件隔离，不做网络隔离，等于没隔。要测网络扫描，不要只测文件列表。

### 3.4 同一用户的多个 Bot 共享 VM，只做权限区分

- 同一用户的多个 Bot 共享 VM，不做硬隔离，只做权限区分：各自的工具白名单、工作目录、可用连接器。
- 审批和预算按 Bot 记账：每个 Bot 的 Mandate 和工具白名单由控制面下发，权限代理按 Bot 身份拦截。这样“采购 Bot 能下单、巡检 Bot 只能读”的约束在同一台 VM 里也成立。
- 用户级记忆所有 Bot 共享（例如“周末不下单”），Bot 私有工作记忆不串（MVP5 已定，本 change 只验证，不重做）。

### 3.5 宿主机多 VM 的资源调度

- 每台 VM 设资源配额，超了就限流，不是一台 VM 把整台服务器吃光。
- 空闲 VM 休眠，释放内存。休眠时发飞书消息，先排队，唤醒后照常回复，不丢消息。
- 预热池：常备几台已经启动好的空 VM，新用户开通时直接分配，不用等冷启动。
- 记录单机密度和唤醒延迟：单台服务器能跑多少台 VM、唤醒要几秒，都要实测，写进 handoff。
- 迁移流程：准备好把用户 VM 迁到另一台服务器的流程，持久磁盘可迁移，或用快照恢复。服务器要维护、要扩容，没有迁移流程就动不了。

### 3.6 控制面要做的事：开通、销户、计量、监控

- **飞书网关**：作为唯一消费者，先按飞书 `open_id` 找到用户和对应 VM，再在 VM 内按会话或频道路由到具体 Bot。
- **租户开通**：开通一台 VM、预装账号、建租户的记忆和技能库、建租户的知识库命名空间。
- **租户销户**：销户要包含数据删除和导出。先导出给客户，再彻底删除，删除要有记录，不能只删 VM 就算销户。
- **监控告警**：VM 死了、磁盘满了、CPU 爆了，要告警，不要等客户来问。
- **按租户计量计费**：每个租户的 token 花费、VM 运行时长、存储用量，都要分开记，复用 MVP2b 的双口径预算记法。

### 3.7 预装账号

- VM 里预装账号，Bot 能代客户去点、去授权。
- 客户也能在 VM 上注册自己的邮箱，像 Grok Bot 那样。
- 预装账号的凭证在 Vault 里，不在 VM 的明文文件里。Bot 拿到的永远是临时替身 token，不是真凭证（MVP2b 已定，本 change 只验证，不重做）。

### 3.8 知识库、记忆、技能的存放和加载（纠正 MVP5 的简化写法）

这是本 change 要纠正的一点，写清楚：

- **本体在控制面**：长期记忆、技能库、知识库、Ontology，本体都在控制面。Postgres 存结构化数据，向量库存向量，对象存储存文件原件。
- **VM 按需取，不加载全量**：VM 启动时不加载全量记忆和技能副本。只按 Ticket 按需检索 Top-K，用完就从上下文里清掉。知识库和技能库再大，VM 还是 4GB 内存。
- **实时数据不进知识库**：库存、订单状态、实时价格，必须实时去查数据库 / ERP / 平台 API，不能从知识库里查。知识库只存相对稳定的认知和参考知识（产品知识、SOP、平台规则、历史案例、对各家 Personal Agent 的理解）。这是 2026-11-26 用户纠正过的定义。
- **Ontology 域共用一份**：基础 Ontology 全租户共用，租户扩展层按客户分，Bot 只拿自己需要的切片，不是一个 Bot 一份。

### 3.9 私有部署和许可证

- 核心逻辑留在厂商云端，客户只跑 Worker，必须回连控制平面；或用编译好的容器镜像，不给源码。
- Apache 2.0 允许闭源分发衍生版本，但必须保留 `LICENSE`、`NOTICE` 和第三方许可证，`third_party/cua-driver/` 等组件也有各自条款。
- `enterprise/` 目录不能未经授权分发。SaaS / 托管要先拿到 Milind Soni 的商业许可，再卖。
- 私有部署只给大客户，只跑运行层，不给源码。价格要比 SaaS 高，合同里写清楚。

## 5. 风险

- 选型选错，跑起来才发现冷启动太慢、内存不够。防法：先做技术验证，再写正式代码。
- 审计记录只存在 VM 里，Agent 能改。防法：审计、审批、Ticket 都存在控制面。
- 隔离只做了文件隔离，没做网络隔离。防法：VM 之间网络互不可达，要测网络扫描。
- 私有部署把源码给出去了。防法：核心逻辑留在厂商云端，客户只跑 Worker，必须回连控制平面。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
