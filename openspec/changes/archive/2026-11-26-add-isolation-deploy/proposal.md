## 为什么改

- 前面五个 MVP 都是在一台长期 VM 上模拟的：私聊、工单、审批、路由、巡检、记忆、技能，都跑通了，但都跑在同一台机器上。真要卖给别人，必须做到：A 客户看不到 B 客户的文件、订单、浏览器登录，网络也互不可达；一台 VM 坏了、重启了，状态和审计记录还在；客户走了，数据能导出、能彻底删除。
- 没有这一层，产品只能自己用，卖不出去。MVP6 就是把“自己用的原型”变成“能卖的产品”的最后一步。
- 时间按新版 roadmap 是 **4–8 周**，不是旧版的 2–4 周。技术验证从 MVP2 就应该开始抽时间做，不要等到 MVP6 才开始选型。

## 改什么（范围）

只加隔离与部署，不改 Ticket 生成、不改审批、不改路由、不改巡检、不改记忆与技能：

1. **一用户一台 microVM，带持久磁盘；同一台服务器上运行多台**。VM 长期存在，不是随用随弃；状态、会话、工作文件存在持久磁盘上，VM 重启还在。
2. **用户之间隔离**：A 用户看不到 B 用户的文件、订单、浏览器登录，网络也互不可达。VM 之间不能互相访问，VM 只能访问控制面的接口和出口代理。
3. **同一用户的多个 Bot 共享 VM，只做权限区分**：各自的工具白名单、工作目录、可用连接器不同。审批和预算按 Bot 记账：每个 Bot 的 Mandate 和工具白名单由控制面下发，权限代理按 Bot 身份拦截。这样“采购 Bot 能下单、巡检 Bot 只能读”的约束在同一台 VM 里也成立。
4. **宿主机多 VM 的资源调度**：每台 VM 设资源配额（建议默认值 2 vCPU / 4 GB / 20 GB，待 MVP6 验证后定稿）；空闲 VM 休眠，释放内存；记录单机密度和唤醒延迟；准备好把用户 VM 迁到另一台服务器的流程（持久磁盘可迁移，或用快照恢复）。
5. **控制面要做的事**：飞书网关作为唯一消费者，先按飞书 `open_id` 找到用户和对应 VM，再在 VM 内按会话或频道路由到具体 Bot；VM 休眠与唤醒，以及预热池（冷启动时消息先排队，唤醒后投递）；租户开通与销户，销户要包含数据删除和导出；监控告警；按租户计量计费。
6. **预装账号**：VM 里预装账号，Bot 能代客户去点、去授权；客户也能在 VM 上注册自己的邮箱。
7. **私有部署**：核心逻辑留在厂商云端，客户只跑 Worker，必须回连控制平面；或用编译好的容器镜像，不给源码。`enterprise/` 目录不能未经授权分发，SaaS / 托管要先拿到 Milind Soni 的商业许可。
8. **纠正 MVP5 设计里的一处简化写法**：MVP5 的 design.md 3.9 写的是“VM 只加载一份只读副本，启动时加载”。这句话是过度简化，**不要按这句话实现**。正确做法是：长期记忆和技能库的本体在控制面，VM 启动时不加载全量副本，只按 Ticket 按需检索（Top-K），用完就从上下文里清掉。知识库和技能库再大，VM 还是 4GB 内存。本 change 把这条写进 specs，作为验收标准。

## 不动什么（边界）

- 不改 Ticket 生成逻辑：那是 MVP2a 已完成的事。
- 不改审批逻辑：那是 MVP2b 已完成的事。
- 不改路由逻辑：那是 MVP3 已完成的事。
- 不改巡检逻辑：那是 MVP4 已完成的事。
- 不改记忆与技能逻辑：那是 MVP5 已完成的事。本 change 只改记忆和技能的**存放和加载方式**（控制面存全量、VM 按需取），不改分层、复盘、沉淀、Curator、核心技能锁的规则。
- 不做全量 Ontology：不定义 10 个实体、300 个关系，不上图数据库。本 change 只保证 Ontology 的存放和加载方式是对的：Ontology 本体在控制面，域共用一份，Bot 只拿自己需要的切片，租户扩展层按客户分。
- 不把实时数据写进知识库：**库存、订单状态、实时价格，必须实时去查数据库 / ERP / 平台 API，不能从知识库里查**。知识库只存相对稳定的认知和参考知识（产品知识、SOP、平台规则、历史案例、对各家 Personal Agent 的理解）。这是 2026-11-26 用户纠正过的定义，本 change 按这个定义写 specs，不要再混在一起。
- 不改 OpenMausBot 核心的 bot 调度、harness 服务；不删模块。
- 不给源码：私有部署只给 Worker 或编译好的镜像，不给项目源码。

## 验收标准

- [ ] A 客户的 Bot 看不到 B 客户的文件和订单。
- [ ] A 用户 VM 内的 agent 主动扫描网络，访问不到 B 的 VM 和控制面内部接口。
- [ ] VM 重启，状态、审计记录还在（审计记录以控制面为准，VM 里最多留一份副本）。
- [ ] VM 休眠时发飞书消息，唤醒后照常回复，不丢消息。
- [ ] 销户后数据可导出，之后彻底删除。
- [ ] 同一用户的多个 Bot 共享 VM，只做权限区分：采购 Bot 能下单，巡检 Bot 只能读。
- [ ] VM 启动时不加载全量记忆和技能副本，只按 Ticket 按需检索 Top-K。
- [ ] `openspec validate --all --strict --no-interactive` 通过；`tasks.md` 全勾完；`handoff.md` 写清楚。

## 风险

- 选型选错，跑起来才发现冷启动太慢、内存不够。防法：先做技术验证，再写正式代码，见 design.md 3.1。
- 审计记录只存在 VM 里，Agent 能改。防法：审计、审批、Ticket 都存在控制面，VM 里最多留一份副本。
- 隔离只做了文件隔离，没做网络隔离。防法：VM 之间网络互不可达，VM 只能访问控制面接口和出口代理，要测网络扫描。
- 私有部署把源码给出去了。防法：核心逻辑留在厂商云端，客户只跑 Worker，必须回连控制平面；或用编译好的镜像，不给源码。
- 隔离环境验证：凡是涉及写入的验证，只能在隔离测试环境中做，不能用正在运行的应用或真实数据。
