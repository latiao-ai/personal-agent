## 设备断网恢复后的标记消息（2026-11-26）

维护者确认网络恢复后发送「断网恢复复检」。飞书开放平台于 10:57:22.610 记录 `im.message.receive_v1`、EventID `4bf135d1e69fdf52d83aaa57a5322134`、首次 `SUCCESS / HTTP 200`、重试次数为零。飞书客户端显示该原消息，但当前验证进程的 JSONL 最后记录仍为 10:52:21.773；网关 SQLite 仍止于序号 16，测试会话未出现该消息或其回复。两者均不存在 EventID 对应的接收记录，因此全断网后的端到端恢复未通过验证，平台 200 不能证明当前网关消费了事件。

检查时 PID 74886（目标网关）和 PID 86400（`lark-cli`）都保持到飞书长连接地址的 TCP 连接。`lark-cli` 的事件总线目录为 `~/.lark-cli/events/<已脱敏应用 ID>/`，其中应用 ID 与「辣条」完全相同。其 `bus.log` 在 10:57:22 记载 EventID `4bf135d1e69fdf52d83aaa57a5322134` 已被 `lark-cli` 长连接收到；同秒平台日志记载同一事件首次 SUCCESS / HTTP 200。PID 74886 的 WebSocket 验证日志及 SQLite 均无该事件。聊天显示原消息，未显示机器人回复。因此本次事件由另一个客户端接收，未进入目标网关。此前 10:17:57 的首条「回复1」也在该总线日志中以相同 EventID 记为收到，而目标网关没有该事件记录。

这将本轮丢消息原因定位为同一 App ID 同时启动了 `lark-cli` 和项目网关的多个 WebSocket 消费者。飞书对同一应用的长连接按集群方式分配事件，客户端间不广播；不同消息可能进入不同客户端。该结论同时解释了原三条测试第一条由 CLI 收到、第二条重试最终进入网关、第三条直接进入网关。此前「CARD 分支」与本案普通消息分流无关。官方 SDK CARD 事件缺陷只涉及卡片互动。后续测试应停止所有使用该 App ID 的 `lark-cli` 接收进程，只运行项目网关。
