## 首次实施

1. 打开本版 `proposal.md`、相关任务、适用规范及目标目录开发约定。摘要中的授权状态只是索引；核对版本、范围、验收条件及维护者的原始消息或可核实评审。无法核实、已撤回或版本不符时，先补齐依据再实施。
2. 用 `git status --short --branch --untracked-files=all` 确认分支、待提交路径及有无重叠。只对目标路径查看 `git diff -- <路径>` 和 `git diff --cached -- <路径>`；新增未跟踪文件直接打开。涉及接口、架构或多模块约束时补读相关 `design.md` 段落和关联代码，既有规范按能力名查阅。
3. 同一会话、同一版本和已确认的范围内，连续编辑、补测及修复相关失败可直接继续。换人、换工作树或上下文压缩后，先恢复摘要，写前重核上述依据。发现新提交、他人改动或所有权冲突时，重新核对受影响的路径。跨机器接手需要双方能取得的提交或补丁。

## 从提案到最终审计

| 阶段 | 智能体负责什么 |
| --- | --- |
| 提案 | 调研并在活动变更中写明版本、范围、影响、验收与撤回办法。小改可用短提案，复杂设计另写。向维护者展示方案。 |
| 确认与实施 | 收到维护者对本版的明确确认后，登记可核实出处并按范围实施。实质扩围、权限或验收变化先升版、确认；撤回后停止实施。修订时保留旧提案可访问的提交或只读快照，并保留与旧版对应的授权。 |
| 验证与送审 | 按任务记录结果。对照本变更全部实际文件（含暂存和未跟踪）、证据及恢复方式，运行 `openspec validate <变更名> --strict`。维护者从同一份交接审计。 |
| 归档 | 维护者最终接受后记录验收出处，完成收尾任务。执行 `openspec archive <变更名>`，更新本页活动入口，再执行 `openspec validate --all --strict`；在 `openspec/specs/` 查生效行为，在 `changes/archive/` 按编号查历史。 |

OpenSpec 的材料就绪、任务勾选与维护者的确认分别留证。实施授权和最终审计是两次不同的决定。仓库指令由客户端执行；Markdown 与 YAML 自身不拦截写入。

## 交接怎样写

每项变更沿用一份 `handoff.md`。首个 `##` 前用几行写 **编号与版本、主执行者、授权状态及出处位置、分支与基线、最近验证、阻塞或下一步**。已确认与待最终验收可以同时成立。摘要不足以回答的问题，指向同文件标题、提案或任务编号。

二级标题以下保留版本确认记录、逐文件用途、验证命令与结果、未验证项、最终决定和恢复方法。按获准、撤回、验证、阻塞、移交等检查点更新；摘要随当前状态更新，历史决定与证据按版本保留。任务勾选只维护在 `tasks.md`。多个变更涉及同一路径时，交接中记录执行者约定的修改顺序。
